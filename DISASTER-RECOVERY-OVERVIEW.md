# Disaster Recovery — универсальная обзорная процедура (pLTE in Box / open5gs-compose)

> **Тип документа:** верхнеуровневый, деплой-независимый. Описывает концепцию, уровни восстановления, сценарии и требования к готовности DR для **любого** варианта деплоя решения.
> Пошаговая инструкция с командами, путями и адресами **конкретного** стенда — [DISASTER-RECOVERY.md](DISASTER-RECOVERY.md) (раздел 8 описывает, как инстанцировать её для нового деплоя).

## 1. Назначение и область применения

Документ определяет концепцию и общий порядок действий по резервному копированию и восстановлению (Disaster Recovery, DR) решения **pLTE in Box** — контейнеризованного ядра мобильной сети на базе Open5GS (4G: MME/HSS/PCRF/SGWC/SGWU; 5G: NRF/AMF/SMF/UPF + eUPF), с WebUI, мониторингом и **шифрованием данных абонентов** (Percona Server for MongoDB, Data-at-Rest encryption) с управлением ключами через KMS (OpenBao).

**Цели DR-процедуры:**

1. гарантировать восстановление услуги после отказа любого компонента — от одиночного контейнера до полной потери узла/площадки (в двухузловой топологии отказ одного узла услугу не прерывает);
2. минимизировать потерю данных абонентов (RPO) и время простоя (RTO);
3. исключить **безвозвратную** потерю данных из-за утраты криптоматериала (ключей шифрования).

**Область применения:** любые деплои решения — лабораторный стенд, стенд интеграции, опытная эксплуатация — независимо от IP-адресации, числа и типов стыков с RAN/транспортной сетью, состава запускаемых профилей (4G/5G/мониторинг/RAN-симуляторы).

**Аудитория:** эксплуатация/администраторы (исполнение процедур), руководство (согласование целевых RTO/RPO), аудит/ИБ (контроль готовности).

**Класс критичности.** Класс критичности деплоя (Mission critical / Business critical / Business support) — параметр деплоя, фиксируемый в инвентаре (5.4); от него зависят целевые доступность, RTO/RPO и периодичность DR-учений (5.1). Деплои текущей очереди — класс **Business support**.

**Связь с DRP.** План восстановления после высококритичных инцидентов (DRP) — **отдельная процедура и сервис**: роли, активация, эскалация и коммуникации здесь не дублируются. Настоящая DR-процедура — техническая основа сценариев восстановления, на которую DRP ссылается (соответствие сценариев рисковым событиям — 4.6).

**Топологии деплоя.** Процедура покрывает обе целевые топологии: **одноузловой** деплой (текущие стенды) и **двухузловой active-active** — Вариант B схемы резервирования: общий пул IP-адресов абонентов, ECMP per-flow в DN + пересылка «чужого» downlink между UPF через IPIP (см. [../redundancy_scheme.md](../redundancy_scheme.md)). Позиции, специфичные для двухузловой топологии, помечены «(2 узла)».

## 2. Архитектурная модель и критичные ресурсы

С точки зрения DR решение состоит из групп ресурсов (пятая — только в двухузловой топологии):

| Группа | Компоненты | Состояние (что теряем) | Источник восстановления |
|---|---|---|---|
| **Ядро сети** | Open5GS (CN), eUPF, NAT, WebUI, мониторинг, RAN-симуляторы | Конфигурация (в git); состояние — не критично (перерегистрация) | git-репозиторий + `.env` |
| **Данные абонентов** | MongoDB/PSMDB с Data-at-Rest encryption | Зашифрованные файлы БД (подписчики, учётные записи) | Логический дамп и/или физический бэкап |
| **Криптоинфраструктура** | KMS (OpenBao): хранилище секретов + ключи | Мастер-ключ шифрования БД (KEK), unseal-key, root-token, TLS | Бэкап KMS (хранилище + ключи — нераздельно) |
| **Инфраструктура** | Хост (ОС, systemd, тюнинг), сетевые настройки (IP, маршруты, стыки), docker-сети | Сетевая связность, автозапуск | Бэкап сетевой конфигурации + git |
| **Межузловая связка** (2 узла) | IPIP-канал UPF↔UPF (2+ линка), ECMP в DN, координация пулов IP, двойные NG-контексты gNB | Маршрутизация downlink между узлами, связность узлов | Сетевая конфигурация хостов + настройки DN (вне решения) |

**Ключевой архитектурный факт** — цепочка криптозависимостей (в двухузловой топологии — **независимо на каждом узле**: свой KMS, свой KEK, своя БД):

```
unseal-key  → расшифровывает →  хранилище KMS  → содержит →  мастер-ключ (KEK)
                                                                  ↓ расшифровывает
                                              файлы БД (.wt)  →  данные абонентов
```

Из неё следуют три главных правила DR:

1. **Потерян unseal-key ⇒ зашифрованное хранилище KMS не расшифровать никогда** ⇒ данные БД (включая все физические бэкапы) потеряны безвозвратно, если нет логического дампа.
2. **Реинициализация KMS (новое хранилище) ⇒ новый KEK** ⇒ все ранее снятые физические бэкапы БД становятся нечитаемыми; спасает только логический дамп.
3. **Бэкап KMS и бэкапы БД — связанные пары**: физический бэкап БД пригоден только вместе с бэкапом KMS, снятым **не позже** него (тот же KEK). В двухузловой топологии пары формируются **в пределах узла** (у каждого узла свой KEK).

**Второй ключевой архитектурный факт (2 узла)** — active-active **без репликации состояния сессий**: PDU-сессия (PDR/FAR/QER, N3 TEID, NAS-контекст) существует только в узле-якоре. Отказ узла ⇒ абоненты выполняют повторную регистрацию (re-attach) на живом узле: секунды; статически назначенные IP **сохраняются** (общий пул), динамические выделяются заново из того же пула. Это осознанное ограничение схемы резервирования (репликация состояния сессий между ядрами в 3GPP не стандартизована).

## 3. Уровни восстановления

Процедура DR разделена на пять уровней — по масштабу аварии и требуемому вмешательству:

| Уровень | Масштаб аварии | Механизм восстановления | Участие человека | Целевой RTO | Целевой RPO |
|---|---|---|---|---|---|
| **L0** | Штатный сбой: перезагрузка хоста/узла, падение контейнеров; (2 узла) обрыв одного из 2+ IPIP-линков | Автоматический: systemd-автозапуск стека, авто-unseal KMS, авто-получение KEK БД; ECMP/LACP переключает межузловой канал на оставшиеся линки | Не требуется | минуты | 0 |
| **L1** | Отказ/потеря отдельного компонента **на узле**: данные БД, хранилище KMS, ключи, TLS, конфигурация | Восстановление компонента из бэкапа | Администратор | 15–30 мин | ≤ интервала бэкапа |
| **L2** (2 узла) | Отказ/потеря **одного узла пары** (ядро целиком или UPF) | Услуга продолжается на втором узле: абоненты отказавшего выполняют re-attach (статические IP сохраняются — общий пул); сам узел восстанавливается планово по процедуре L4 | Администратор (восстановление узла — плановое, без спешки) | секунды (re-attach) — для услуги; узел — в согласованное окно | 0 — данные не теряются |
| **L3** | Потеря сетевой конфигурации хоста (IP-адреса, маршруты, стыки, VLAN); (2 узла) включая IPIP-связку и ECMP в DN | Восстановление сетевых настроек + перезапуск стека | Администратор (с консоли хоста) | 15–30 мин | 0 (данные не страдают) |
| **L4** | Полная потеря хоста/узла (диск/ОС), обоих узлов/площадки; миграция на новое железо | Развёртывание с нуля: ОС → Docker → сеть → конфигурация → KMS → БД → запуск | Администратор | 1–2 часа (на узел) | ≤ интервала бэкапа (0 — при физическом) |

> Уровень определяется **масштабом повреждения**, а не его причиной: аппаратный отказ, ошибка администратора, вредоносное действие или плановая миграция — процедура одна и та же.
>
> **Одноузловой деплой:** уровень L2 отсутствует (отказ единственного узла = L4). Соответствие нумерации деплой-специфичного [DISASTER-RECOVERY.md](DISASTER-RECOVERY.md) (одноузловой стенд): его L2 (сетевая конфигурация) = L3, его L3 (полная потеря) = L4.

## 4. Сценарии восстановления

### 4.1 L0 — штатная перезагрузка (автоматическое восстановление)

**Концепция:** при загрузке хоста systemd-юнит поднимает стек, инициализационный скрипт применяет тюнинг хоста (CPU, сетевые буферы, affinity), KMS автоматически снимает seal по локально сохранённому unseal-key, СУБД получает мастер-ключ и открывает шифрованное хранилище. Данные абонентов — на диске, потерь нет.

**Требуется:** установленный и включённый systemd-юнит; ключи KMS на месте; корректная сетевая конфигурация хоста (восстанавливается ОС из своих настроек).

### 4.2 L1 — компонентные сценарии (на узле)

| Сценарий | Что потеряно | Требуемые бэкапы | Результат |
|---|---|---|---|
| **БД-данные** | Файлы БД повреждены/удалены | Логический дамп (KMS цел) — базовый вариант; физический бэкап + бэкап KMS — без потерь | Данные с точностью до последнего дампа / до момента снятия физического бэкапа |
| **Хранилище KMS** | Данные хранилища секретов | Бэкап KMS (хранилище + ключи, пара) + физический бэкап БД **или** логический дамп | С тем же KEK — без потерь; без бэкапа KMS — только реинициализация + логический дамп |
| **Ключи KMS** | Unseal-key / root-token | Логический дамп БД (физические бэкапы БД и хранилище KMS становятся непригодны) | Реинициализация KMS, новый KEK, restore из дампа |
| **TLS-сертификаты** | Сертификаты KMS | Не требуются — регенерация | Без потерь данных; перезапуск KMS + СУБД |
| **Конфигурация** | `.env`, compose-файлы, код | Git (remote или bundle) + копия `.env` | Без потерь данных; пересоздание контейнеров |

**Общий порядок любого L1-сценария:** остановить затронутые сервисы → изолировать повреждённое (не удалять сразу) → подготовить чистое место восстановления (для БД — пустой каталог с правильными правами, т.к. шифрование включается только на пустом хранилище) → восстановить из бэкапа → поднять стек → верифицировать (раздел 7).

### 4.3 L2 — отказ одного узла в паре (2 узла, active-active)

**Концепция:** при отказе узла (ядро целиком или только UPF) услуга **не прерывается**: gNB направляет uplink только в якорный узел (по N3 TEID), абоненты отказавшего узла выполняют повторную регистрацию (re-attach) на живом узле — повторная аутентификация, новая PDU-сессия, секунды. Статически назначенные IP **сохраняются** (пул общий); динамические выделяются заново из того же пула. Downlink перестаёт пересылаться по IPIP на отказавший узел — живой узел находит все сессии у себя. Восстановление самого узла — **плановое**, в согласованное окно, по процедуре L4 для одного узла: второй узел держит услугу, спешка не требуется.

**Требуется:** профили абонентов согласованы на обоих узлах (иначе re-attach невозможен); gNB имеет два NG-контекста; ECMP в DN и IPIP-связка сконфигурированы.

**Смежные сценарии двухузловой схемы (Вариант B):**

| Сценарий | Признаки | Механизм / действия | Уровень |
|---|---|---|---|
| Обрыв одного из 2+ IPIP-линков | Деградация пропускной способности межузлового канала, сервис жив | Автоматически: ECMP/LACP перенаправляет на оставшиеся линки | L0 |
| Полный обрыв IPIP-связки | Оба узла живы; ~50% downlink теряется (хешированное на неякорный UPF не пересылается); uplink не затронут | Восстановление связности (транспорт/сетевая конфигурация); до восстановления TCP-потоки спасает ретранссия, UDP-сервисы деградируют | L3 |
| Рассинхронизация профилей абонентов между узлами | Re-attach на живом узле отклоняется (абонент неизвестен); `upf_ipip_loop_dropped_total` > 0 — признак рассинхрона PDR | Повторная синхронизация данных абонентов (механизм — параметр деплоя, раздел 8); источник истины — по регламенту деплоя | L1 |
| Коллизия динамических IP (одинаковый IP выдан обоими узлами) | Нарушение доставки downlink одному из абонентов | Устранение пересечения динамических субпулов; повторное выделение адресов | L1 (конфигурация) |
| Устаревшая (stale) IDLE-сессия после re-attach | ~50% loss downlink для абонента; бессмысленный paging из старого узла | Штатно в UPF: rebalance при non-FORW FAR (пересылка пиру) + NOCP-нотификация для cleanup | L0 (штатно) |

### 4.4 L3 — потеря сетевой конфигурации хоста

**Концепция:** данные (БД, KMS, конфигурация) не страдают — восстанавливается только связность. Типовые симптомы: стек не поднимается из-за отсутствия на хосте IP, к которому привязаны порты; недоступны стыки с RAN (S1/N3, SCTP/GTP-U) и транспортной сетью (N6/SGI); пропали VLAN-интерфейсы; (2 узла) нарушена межузловая связка: IPIP-подсеть недоступна, ECMP в DN перестал обслуживать оба UPF.

**Требуется:** бэкап сетевой конфигурации хоста (netplan или эквивалент: статические IP, VLAN, маршруты до GTP-пилотов и шлюзов; 2 узла — включая IPIP-подсеть и адреса пиров UPF) + контрольные снимки фактического состояния (`ip addr/route/rule`, firewall) для сверки.

**Порядок (концептуально):**

1. Восстановить сетевую конфигурацию из бэкапа; применять **только с консоли хоста** (IPMI/монитор) — применение по SSH может оборвать доступ; безопасный режим — с автооткатом по таймеру (`netplan try`).
2. Сверить IP/маршруты/правила с контрольным снимком.
3. Перезапустить стек с пересозданием контейнеров: контейнеры с портами, привязанными к IP хоста, при отсутствии IP уходят в restart-loop и сами не восстанавливаются.
4. Проверить стыки (доступность GTP-пилотов, SCTP-ассоциации, маршрут по умолчанию для N6) и docker-сети.

**Docker-сети восстановления не требуют** — они полностью описаны в compose-файлах и пересоздаются при подъёме стека (включая статические IP контейнеров).

### 4.5 L4 — полная потеря узла/площадки / развёртывание с нуля

**Концепция:** восстановление на чистый хост ОС (Ubuntu) из комплекта бэкапов. Порядок шагов **важен** — каждый следующий зависит от предыдущего. В двухузловой топологии узлы восстанавливаются **последовательно** (начиная с любого — второй держит услугу); после восстановления обоих — сверить согласованность профилей абонентов и межузловую связку (IPIP, ECMP в DN).

```
1. ОС + базовые пакеты + Docker
2. Сетевая конфигурация хоста (стыки, IP, маршруты)   ← ДО подъёма стека: порты привязаны к IP хоста
3. Репозиторий решения + .env (в тот же путь/имя каталога!)
4. TLS-сертификаты KMS
5. KMS: хранилище + ключи (нераздельная пара)
6. БД: физический бэкап (с тем же KEK) или чистый каталог + логический дамп
7. Запуск стека, установка systemd-автозапуска
8. Верификация (раздел 7)
```

**Требуется:** полный комплект бэкапов (раздел 5.2) + доступ к приватным реестрам образов (или сохранённые образы) + консольный доступ к хосту.

### 4.6 Соответствие обязательным рисковым событиям

Сценарии процедуры покрывают обязательные рисковые события (перечень — по корпоративному подходу к DRP):

| Рисковое событие | Покрытие |
|---|---|
| Потеря ЦОД/площадки | L4 — полная потеря узла/площадки (4.5) |
| Потеря/уничтожение данных (БД) | L1 — сценарий «БД-данные» (4.2) |
| Потеря нод | 2 узла: L2 — отказ узла в паре (4.3); 1 узел: L4 (4.5) |
| Шифрование данных (ransomware) | Восстановление из верифицированных чистых бэкапов (L1/L4) с ротацией ключей — [PSMDB-ENCRYPTION.md](PSMDB-ENCRYPTION.md); страховка — логический дамп (снимается в plaintext, хранить зашифрованным вне стенда) |
| Массовое вирусное заражение | Переустановка ОС + восстановление L4 из чистых бэкапов; бэкапы offsite (5.3) |
| DDoS-атака; отзыв внешнего SSL-сертификата | **Неприменимо:** решение эксплуатируется в закрытом контуре, внешний SSL-сертификат не используется |

> Роли, активация, эскалация и коммуникации при высококритичных инцидентах — в отдельной процедуре DRP; настоящая процедура — техническая основа восстановления, на которую DRP ссылается.

## 5. Требования к DR-готовности

### 5.1 Целевые показатели по классу критичности

Класс критичности — параметр деплоя (5.4). Нормативные и целевые значения — по корпоративным НД: «Нормативные и целевые значения метрик надежности» (актуальная редакция), СТ-Э-055-2 (приложения 15, 16):

| Показатель | Mission critical | Business critical | **Business support** (текущие деплои) |
|---|---|---|---|
| Доступность | 99.95% | 99.5% | **99%** |
| Бюджет ошибок (год / месяц / неделя) | 4 ч 23 м / 22 м / 5 м | 43 ч 50 м / 3 ч 39 м / 50 м | **87 ч 39 м** / 7 ч 18 м / 1 ч 41 м |
| RTO | не более 2 ч | не более 4 ч | **не более 24 ч** (норматив: t + не менее 6 ч, где t — время восстановления площадки) |
| RPO | не более 1 ч | не более 4 ч | **не более 24 ч** ⇒ интервал бэкапа БД — не реже чем каждые 12 ч (запас ×2 к нормативу) |
| Частота DR-учений | не реже 1 раза в 3 мес. | не реже 1 раза в 6 мес. | **не реже 1 раза в 12 мес.** |

> По НД: подтверждение соблюдения нормативов — по фактическим значениям тестирования DRP и устранения реальных сбоев; пересмотр значений — ежегодно.

Фактические оценки решения (разделы 3–4) укладываются в нормативы Business support с запасом: RTO услуги — минуты (L0–L3) и 1–2 ч на узел (L4); в двухузловой топологии отказ одного узла — секунды (re-attach), услуга не прерывается.

### 5.2 Обязательный комплект бэкапов

| # | Артефакт | Статус | Периодичность | Шифрование при хранении |
|---|---|---|---|---|
| 1 | Логический дамп БД (`mongodump`) | **Обязателен всегда** — единственная страховка от потери ключей | Ежедневно (минимум); для BS — не реже чем каждые 12 ч (5.1) | **Да — дамп всегда plaintext!** |
| 2 | Физический бэкап БД (зашифрованные файлы) | Опционален; даёт RPO=0 на момент снятия | По расписанию / перед изменениями | Уже зашифрован KEK |
| 3 | Состояние KMS: хранилище + unseal-key / root-token (**пара, нераздельно**) | **Критично** | Ежедневно / при изменениях | Да |
| 4 | TLS-сертификаты KMS | Важно | При каждой генерации | Да |
| 5 | Конфигурация: git-репозиторий (bundle) + `.env` | Важно | Ежедневно / при изменениях | Да (`.env` может содержать чувствительное) |
| 6 | Сетевая конфигурация хоста (netplan + контрольные снимки `ip`/firewall; 2 узла — включая IPIP-подсеть и адреса пиров UPF) | Важно | При каждом изменении + периодический контроль | Да |
| 7 | Образы из приватных реестров (eUPF и др.) | Зависит от окружения | При обновлениях | — |
| 8 | systemd-юнит и хостовый тюнинг | Важно | При изменениях (код — в git) | — |

**Двухузловая топология:** комплект снимается **с каждого узла независимо** (у каждого узла свой KMS/KEK и своя БД). Пары «бэкап БД узла + бэкап KMS узла» маркируются по узлу и не смешиваются: физический бэкап БД узла N валиден только с бэкапом KMS узла N (тот же KEK).

### 5.3 Правила хранения

- **Правило 3-2-1:** 3 копии, 2 разных носителя, 1 — вне стенда (offsite).
- Бэкапы KMS и логические дампы БД хранить **раздельно**: вместе они дают расшифровку всех данных абонентов.
- Парольные фразы (для шифрования бэкапов) — в менеджере паролей / запечатанном конверте, отдельно от носителей с бэкапами.
- Ротация с проверкой: перед удалением старой копии убедиться, что новая проходит проверку целостности (листинг/распаковка архива).
- После успешного восстановления — удалять промежуточные plaintext-артефакты (распакованные дампы, изолированные повреждённые каталоги).
- (2 узла) Бэкапы разных узлов хранить раздельно, с маркировкой узла: у каждого узла свой KEK, пары «БД + KMS» между узлами не смешивать.

## 6. Критические принципы (инварианты; нарушение = потеря данных)

1. **Unseal-key и хранилище KMS — нераздельная пара.** Потеря unseal-key без бэкапа = безвозвратная потеря всех зашифрованных данных.
2. **Реинициализация KMS = новый KEK** ⇒ все физические бэкапы БД непригодны; единственный путь восстановления — логический дамп.
3. **Логический дамп — всегда открытый текст** ⇒ шифровать немедленно после снятия, исходник удалять.
4. **Физический бэкап консистентен только при остановленной СУБД.**
5. **Шифрование хранилища включается только на пустом каталоге БД** ⇒ перед restore — всегда чистый dbPath.
6. **Права на файлы БД** — внутренний UID процесса СУБД в контейнере ⇒ после восстановления восстанавливать владельца.
7. **Имя каталога проекта задаёт имена контейнеров/сетей/томов** ⇒ при восстановлении сохранять то же имя каталога.
8. **Сеть — до стека:** порты привязаны к IP хоста; изменения сетевой конфигурации применять только с консоли.
9. **Команды восстановления выполнять в shell на сервере** — не через удалённые обёртки/клиенты, искажающие символы.
10. **(2 узла) ECMP в DN — строго per-flow (5-tuple)** ⇒ per-packet хеширование недопустимо (переупорядочивание пакетов в потоках).
11. **(2 узла) Отсутствие NAT/PAT на N6** ⇒ DN видит реальный IP абонента — обязательное условие поиска сессии по DST IP (miss-правило IPIP-пересылки).
12. **(2 узла) 2+ независимых IPIP-линка** ⇒ одиночный линк = SPOF: его полный обрыв = потеря ~50% downlink для всех абонентов.
13. **(2 узла) MTU межузлового канала ≥ MTU N6 + 20** ⇒ IPIP добавляет 20 байт внешнего заголовка; ICMP FragNeeded приходит на UPF, а не на отправителя в DN (PMTU-ловушка).
14. **(2 узла) Динамические субпулы внутри общего пула — непересекающиеся** ⇒ иначе оба узла могут выдать один и тот же IP разным абонентам.
15. **(2 узла) Профили абонентов согласованы на обоих узлах** ⇒ иначе re-attach на живой узел невозможен: рассинхрон превращает отказ узла в отказ услуги.
16. **(2 узла) Криптоцепочка и пары бэкапов — в пределах узла** ⇒ физический бэкап БД узла N валиден только с бэкапом KMS узла N (у каждого узла свой KEK).

## 7. Верификация и регулярные проверки

**После каждого восстановления (обязательный минимум):**

- все сервисы стека — запущены/healthy (по составу профилей деплоя);
- KMS — unsealed; СУБД — открыла шифрованное хранилище (признаки шифрования в логе);
- данные абонентов читаются (число записей соответствует бэкапу);
- интерфейсы управления (WebUI и др.) отвечают; TLS до KMS проходит проверку цепочки;
- сетевые стыки: доступность GTP-пилотов, SCTP-ассоциации с RAN, NAT/маршрутизация UE-подсети;
- (2 узла) межузловая работа: re-attach на живой узел выполняется, статические IP сохраняются; метрики `upf_ipip_*` в норме (`upf_ipip_loop_dropped_total` = 0); ECMP-баланс downlink между UPF соответствует расчётному.

**Периодический контроль готовности:**

- проверка целостности бэкапов (листинг/распаковка архивов) — с той же периодичностью, что и снятие;
- **DR-учения по нарастающей:** штатная перезагрузка (L0) → компонентные восстановления на **копиях** данных (L1) → (2 узла) отказ одного узла в паре на лабораторном стенде (L2) → восстановление сетевой конфигурации с консоли (L3) → полная репетиция L4 на отдельном железе/ВМ. Периодичность — по классу критичности (5.1); для Business support — **не реже 1 раза в 12 месяцев**;
- повторение учений после каждого значимого изменения конфигурации решения.

## 8. Адаптация процедуры к конкретному деплою

1. Заполнить **инвентарь деплоя** (5.4): адреса, стыки, профили, пути, интервалы, класс критичности, топологию (1/2 узла) и параметры межузловой связки.
2. (2 узла) Определить и зафиксировать механизм согласования профилей абонентов между узлами (репликация БД / периодический синк / общий источник populate) и источник истины при рассинхронизации.
3. Создать деплой-специфичный документ по образцу [DISASTER-RECOVERY.md](DISASTER-RECOVERY.md): конкретные команды, пути, IP-адреса, имена интерфейсов, чеклисты верификации.
4. Настроить регламент бэкапов (5.2) и выгрузку копий offsite (5.3); убедиться, что бэкап KMS снимается **вместе с ключами** и не позже физического бэкапа БД (2 узла — с каждого узла, пары в пределах узла).
5. Провести базовые DR-тесты (L0, компонентные сценарии на копиях) и полную репетицию L4; для 2 узлов — учение L2 (отказ узла в паре).
6. Включить DR-учения в регламент эксплуатации с периодичностью по классу критичности (5.1); обновлять оба документа при изменении конфигурации.
